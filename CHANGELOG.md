## Changelog
[unrelease]
- [Feature] - Added separate checkout options for Apple Pay, Google Pay, PayPal and Klarna. Each method can be enabled individually with its own checkout label in a new "Single Payment method" section of the module configuration, and is listed as its own payment option. Selecting one restricts the Frisbii charge session to that method (`payment_methods`), with both the embedded and window checkout types. The method sent by the shopper is validated against a server-side allow-list and must be enabled; an unknown or disabled value returns the shopper to checkout without creating a session.
- [Feature] - Added a "Show generic Frisbii option" setting to hide or show the existing card option while method-specific options are enabled. The generic option is always shown when no method-specific option is enabled, and existing installs keep it visible.
- [Feature] - Added a "General payment method" section with the same "Payment Methods", "Payment Logos" and "Logo Height" settings as the WooCommerce plugin. "Payment Methods" restricts the methods offered in the Frisbii payment window of the gen ric option (empty keeps the previous behaviour of sending no `payment_methods`); "Payment Logos" shows the selected logos with the generic option; "Logo Height" also sizes the logos of the method-specific options. Saved lists are filtered against server-side allow-lists and the height is validated as a CSS length.
- [Feature] - Added a "Debug logging" setting (off by default). When enabled, each charge session request is written to Advanced Parameters > Logs with the order handle, the `payment_methods` sent to Frisbii, the checkout type and the result, so method-specific options can be verified without completing a payment. No customer, address or API key data is logged.
- [Fix] - Fixed payment option logos not rendering at checkout: `Media::getMediaPath()` returned an empty image source for a file system path, and the generic option pointed at a `payment.jpg` file that does not exist.
- [Refactor] - Added a `PaymentMethodMap` class as the single source of truth for method identifiers, labels, logos, configuration keys and charge-session payload construction, and a `ChargeSessionLog` class for the log line, both unit tested.
- [Feature] - Click to Pay is now included automatically in the Frisbii payment window: `click_to_pay` is appended once to `payment_methods` whenever the generic option's "Payment Methods" setting already sends `card`, `visa` or `mc`, in both the embedded and window checkout types. No new setting is added; merchants must still be approved for Click to Pay by Frisbii. A "Click to Pay" entry was added to the existing "Payment Logos" list so its prepared logo can be shown next to the generic option.
- [Feature] - Click to Pay is excluded for subscription orders: when the optional Frisbii Subscription module reports that the cart contains a subscription product, `click_to_pay` is left out of the charge-session payload and its logo is hidden at checkout, even if selected in "Payment Logos". Shops without that module are unaffected.

v 1.3.8.1
- [Security] - The webhook endpoint now verifies an HMAC-SHA256 signature from Frisbii before processing any event. Requests that are malformed, unsigned, or signed with an invalid signature are rejected before any cart or order logic runs, closing a gap that previously let a forged webhook request create or modify an order.
- [Feature] - The webhook signing secret is cached for 10 minutes and refreshed automatically (once) if a signature check fails, so Frisbii rotating the secret no longer requires manual intervention. If the secret cannot be retrieved at all, the webhook fails closed and rejects the event.
- [Fix] - The cached webhook secret is now invalidated automatically whenever the private API key is changed in the module configuration, since a new key can belong to a different Frisbii account.
- [Refactor] - Extracted the admin order panel's display logic (card logo lookup, refund control state, dashboard link) into a separate, unit-tested class, and removed a dead code path that queried the Frisbii API for an order event timeline that was never actually displayed.
- [Fix] - Replaced the timing-based workaround for the webhook/confirmation order-creation race (the 5-second sleep plus pre-lock `orderExists()` check added in 1.3.8) with an atomic, database-backed lock (MySQL `GET_LOCK()`/`RELEASE_LOCK()`) shared by both entry points via a deterministic per-cart lock key. The order-existence check and `validateOrder()` now run inside the same lock, the lock is released on every success, redirect, and exception path, and the confirmation redirect resolves the real order id even when the webhook creates the order first. The webhook now returns HTTP 503 (retryable) if the lock cannot be acquired within a bounded timeout, instead of failing silently; the fixed 5-second sleeps in both controllers have been removed.


v 1.3.8
- [Feature] - Added support for Prestashop 9.1.x.
- [Fix] - Fixed "Attempt to read property 'alert_emails' on null" error when saving the module configuration; standardized Reepay API error responses when cURL fails or returns invalid JSON, removed duplicate curl_exec() calls during webhook updates, and added null checks/validation for incomplete or unexpected API responses.
- [Fix] - Fixed webhook not updating on local site environments. Frisbii does not accept webhook URLs using http://localhost; a public test site should be used instead.
- [Fix] - Fixed Frisbii Payments status always showing "Not Authenticated". The authentication check previously required both account name and email, but per the Frisbii API schema only the name is required. Authentication now relies on the account name only; the email is still displayed when available but no longer affects authentication status.
- [Fix] - Fixed HTTP 500 error on the payment confirmation page caused by a race condition between the Reepay webhook and the payment confirmation redirect. Added a 5-second delay before calling orderExists() to give the webhook time to create the order, and wrapped validateOrder() in a try/catch (PrestaShopException) to prevent a fatal error when the webhook creates the order first.
- [Docs] - Updated Readme with detailed step-by-step installation guide for Prestashop.
